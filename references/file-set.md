# การเลือกรายการไฟล์

รายการไฟล์ไม่ตายตัว เลือกตามลักษณะของระบบ หลักคือ **ทุกเรื่องที่ทีมต้องรู้เพื่อเริ่มงานต้องมีที่อยู่ และไม่มีไฟล์ที่ว่างเปล่าเพราะระบบไม่มีเรื่องนั้น**

## ไฟล์แกน มีทุกโครงการ

| ไฟล์ | เนื้อหา | ผู้อ่านหลัก |
|---|---|---|
| `docs/00-source.md` | บันทึกข้อมูลต้นทางที่ได้รับ และข้อแก้ไขที่ผู้ใช้ยืนยัน | ผู้รีวิว |
| `docs/01-overview.md` | ภาพรวม วัตถุประสงค์ ขอบเขต ผู้ใช้ ทีม ข้อจำกัด คำศัพท์ | ทุกคน |
| `docs/02-features.md` | รายการฟีเจอร์แยกตามผู้ใช้ | ทุกคน ใช้คุยกับลูกค้า |
| `docs/03-flows.md` | ลำดับการทำงานแต่ละเรื่อง และสถานะของสิ่งที่ระบบติดตาม | ทุกคน |
| `docs/04-architecture.md` | ส่วนประกอบ การสื่อสาร ข้อเสนอเทคโนโลยี สภาพแวดล้อม | นักพัฒนา |
| `docs/05-data-model.md` | โครงสร้างข้อมูล | นักพัฒนา |
| `docs/06-api-spec.md` | รายการ API และงานตั้งเวลา | นักพัฒนา |
| `docs/NN-decisions.md` | ทุกเรื่องที่ต้องยืนยันกับลูกค้า | หัวหน้าโครงการ ลูกค้า |
| `docs/NN-dev-plan.md` | แบ่งเฟส งาน เกณฑ์ผ่าน ความเสี่ยง | หัวหน้าโครงการ |
| `README.md` | ทางเข้าของทั้งชุด | ทุกคน |
| `plans/` อย่างน้อย 1 ไฟล์ | แผนของงานขั้นถัดไป | ผู้ที่จะทำงานขั้นถัดไป |

`NN` คือเลขนำหน้าที่ได้จากการเรียงในหัวข้อถัดไป

ตัดไฟล์แกนออกได้เมื่อระบบไม่มีเรื่องนั้นจริง ๆ เช่น ระบบที่ไม่มีการเรียกผ่าน API ให้ตัด 06 ออกและรวมงานตั้งเวลาไว้ในไฟล์สถาปัตยกรรม ถ้าตัด ให้บอกเหตุผลไว้ใน README ข้อควรรู้ก่อนอ่าน โดยเรียกไฟล์ที่ตัดด้วยชื่อเรื่องและเลข เช่น "ไม่มีไฟล์รายการ API (เลข 06)" ไม่เขียนชื่อไฟล์ที่มี .md เพราะสคริปต์จะถือว่าอ้างไฟล์ที่ไม่มีอยู่ และไฟล์ถัดไปเลื่อนเลขขึ้นมาแทน ไม่เว้นเลข ไฟล์ลำดับการทำงานและไฟล์ประเด็นตัดสินใจตัดไม่ได้ เพราะทุกระบบมีลำดับการทำงานและทุกชุดเอกสารมีเรื่องที่ทีมเสนอเอง

**คำในชื่อไฟล์ที่สคริปต์ตรวจพึ่ง** `flows`, `decisions`, `screens`, `api`, `data-model` สคริปต์ใช้คำเหล่านี้หาไฟล์เพื่อตรวจการอ้าง Flow การอ้างประเด็น ตารางสรุปประเด็น และนับจำนวนจริง ถ้าเปลี่ยนคำ สคริปต์จะรายงานว่าไม่พบไฟล์หรือข้ามการตรวจนั้น ชื่อไฟล์คงเป็นภาษาอังกฤษแม้เนื้อหาเป็นภาษาอื่น

## ไฟล์เสริม เลือกตามลักษณะของระบบ

ถามตัวเองทีละข้อ ถ้าคำตอบคือใช่ ให้มีไฟล์นั้น ตารางนี้เป็นตัวตัดสิน ไม่มีเพดานจำนวนไฟล์

| ระบบมีสิ่งนี้หรือไม่ | ไฟล์ที่เพิ่ม | เนื้อหา |
|---|---|---|
| มีหน้าจอให้คนใช้ | `NN-screens.md` | หน้าจอแยกตามกลุ่มผู้ใช้ องค์ประกอบ API ที่ใช้ ความสำคัญ |
| เชื่อมกับแพลตฟอร์มหรือบริการภายนอกที่มีรายละเอียดมาก | 1 ไฟล์ต่อการเชื่อมต่อ ตั้งชื่อตามสิ่งที่เชื่อม เช่น `NN-line-integration.md`, `NN-payment.md`, `NN-erp-integration.md` | สิ่งที่ต้องเตรียม ลำดับการเรียก ข้อจำกัดของบริการนั้น รายการทดสอบ |
| มีฮาร์ดแวร์หรืออุปกรณ์ | `NN-hardware.md` | สเปกอุปกรณ์ โปรโตคอล การติดตั้ง รายการทดสอบ |
| ส่งข้อความหรือแจ้งเตือนอัตโนมัติหลายแบบ | รวมไว้ในไฟล์การเชื่อมต่อของช่องทางนั้น หรือแยกเป็น `NN-notifications.md` | รายการข้อความ ส่งเมื่อใด ถ้อยคำตั้งต้น |
| ลูกค้ากำหนดรูปแบบรายงาน หรือรายงานเป็นงานส่งมอบสำคัญ | `NN-reports.md` | รายงานแต่ละฉบับ รูปแบบตาราง แต่ละช่องนับจากอะไร ใครดูได้ |
| เก็บข้อมูลส่วนบุคคล หรือมีข้อกำหนดด้านกฎหมายและความปลอดภัย | `NN-security-pdpa.md` หรือ `NN-security.md` | ข้อมูลที่เก็บ สิทธิ์การเข้าถึง การปกปิด อายุการเก็บ บันทึกการใช้งาน |
| มาแทนระบบเดิม หรือต้องย้ายข้อมูลเดิม | `NN-migration.md` | ข้อมูลที่ย้าย การจับคู่ฟิลด์ ลำดับการย้าย การตรวจหลังย้าย แผนถอยกลับ |
| มีการคำนวณที่ซับซ้อน เช่น ราคา ค่าปรับ คะแนน สิทธิ์ | `NN-business-rules.md` | กฎแต่ละข้อ สูตร ตัวอย่างคำนวณ กรณีขอบ |
| ลูกค้าต้องตรวจรับงานตามรายการ | `NN-acceptance.md` | สถานการณ์ทดสอบที่ลูกค้าใช้ตรวจรับ ผลที่ต้องได้ |

เรื่องเล็กที่ไม่ถึงขั้นต้องแยกไฟล์ ให้เป็นหัวข้อในไฟล์แกนที่ใกล้ที่สุด เช่น ระบบที่ส่งอีเมล 2 แบบ ไม่ต้องมี `NN-notifications.md`

## การเรียงเลขนำหน้า

- เลข 2 หลัก ต่อเนื่อง ไม่ข้าม ชื่อไฟล์ภาษาอังกฤษตัวพิมพ์เล็กคั่นด้วยขีดกลาง
- `00` ถึง `06` ตามตารางไฟล์แกน ถ้าตัดไฟล์แกนใด ไฟล์ถัดไปเลื่อนเลขขึ้นมาแทน ไม่เว้นเลข
- ถัดมาคือไฟล์ที่ไฟล์ลำดับการทำงานต้องพึ่ง ได้แก่ ไฟล์การเชื่อมต่อ ฮาร์ดแวร์ ข้อความและการแจ้งเตือน และกติกาการคำนวณ (ถ้ามี) แล้วรายการหน้าจอ
- แล้วไฟล์ประเด็นตัดสินใจ และไฟล์แผนพัฒนา
- ไฟล์เสริมเฉพาะเรื่อง ได้แก่ รายงาน ความปลอดภัย การย้ายข้อมูล และรายการตรวจรับ ต่อท้ายตามลำดับนี้

ตัวอย่างของระบบรับเรื่องผ่านแชตที่มีรายงานและข้อมูลส่วนบุคคล

ตัวอย่างของระบบจองพื้นที่ที่มีอุปกรณ์ควบคุมประตูและรับชำระเงิน

ถ้าผู้ใช้ระบุรายการไฟล์มาเอง ให้ยึดตามนั้นเป็นหลัก แต่ถ้ามีไฟล์ที่ไม่ตรงกับระบบนี้ หรือมีเรื่องสำคัญที่ไม่มีไฟล์รองรับ ให้เสนอปรับในขั้นที่ 2 พร้อมเหตุผล

## ไฟล์ใน plans/

`plans/` เก็บแผนของ **งานขั้นถัดไป** ที่จะเกิดหลังเอกสารเสร็จ ต่างจากแผนพัฒนาใน docs ซึ่งเป็นแผนทั้งโครงการ

| ระบบเป็นแบบใด | ไฟล์ |
|---|---|
| มีหน้าจอ | `plans/mockup-plan.md` แผนทำหน้าจอตัวอย่างที่กดได้ เพื่อให้ลูกค้าเห็นภาพและปิดประเด็นที่ต้องเห็นก่อนตัดสินใจ |
| ไม่มีหน้าจอ แต่มีความเสี่ยงทางเทคนิค เช่น การเชื่อมต่อ อุปกรณ์ ปริมาณข้อมูล | `plans/poc-plan.md` แผนทดลองพิสูจน์ว่าทำได้จริง |
| มีทั้งสองอย่าง | มีทั้งสองไฟล์ |
| ไม่มีหน้าจอ และไม่มีความเสี่ยงทางเทคนิคที่ต้องพิสูจน์ | `plans/rollout-plan.md` แผนเตรียมเปิดใช้งาน ได้แก่ ข้อมูลตั้งต้น สิทธิ์ที่ต้องขอ ลำดับเปิดใช้ และแผนถอยกลับ |

เพิ่มแผนอื่นได้เมื่อผู้ใช้ขอ เช่น แผนย้ายข้อมูล แผนอบรม

## ขนาดของงาน

ปรับความละเอียดตามขนาดของระบบ ไม่ใช่เขียนให้ยาวเท่ากันทุกครั้ง

- ระบบเล็ก ผู้ใช้กลุ่มเดียว ไม่กี่หน้าจอ: ไฟล์แกนสั้น ๆ กับรายการหน้าจอก็พอ ไฟล์เสริมอื่นมักไม่ต้องมี
- ระบบกลาง หลายบทบาท มีการเชื่อมต่อภายนอก: ไฟล์แกนเต็มรูป รายการหน้าจอ และไฟล์เสริมอื่นตามที่ตอบว่าใช่ในตารางข้างบน มักได้ 1 ถึง 3 ไฟล์
- ระบบใหญ่ หลายระบบย่อย: แบ่งเนื้อหาในไฟล์ฟีเจอร์ ลำดับการทำงาน และ API ตามระบบย่อย ถ้าไฟล์ใดยาวเกินประมาณ 600 บรรทัด ให้พิจารณาแยกไฟล์ตามระบบย่อย ไฟล์ที่แยกต้องคงคำหลักในชื่อ เช่น `03-flows-booking.md`, `04-flows-billing.md` แล้วไฟล์ถัดไปเลื่อนเลขตาม (สถาปัตยกรรมกลายเป็น 05) เลข 00 ถึง 06 ตามตารางไฟล์แกนใช้เมื่อไม่แยกไฟล์ และเลข Flow ต้องไม่ซ้ำกันข้ามไฟล์ คือนับต่อจากไฟล์ก่อน ไม่เริ่ม 1 ใหม่ สคริปต์ตรวจจะรายงานเลข Flow ที่ซ้ำ และพิมพ์ยอดรวม Flow ของทุกไฟล์ ส่วนตารางที่ใช้ร่วมกันอยู่ที่ใดดู `templates.md` หัวข้อ 03-flows.md

ข้อกำหนดที่ให้มาน้อยไม่ได้แปลว่าเอกสารสั้นได้ ระบบที่ลูกค้าเขียนมา 5 บรรทัดอาจมีลำดับการทำงานที่ต้องคิดเพิ่มอีกมาก สิ่งที่คิดเพิ่มทั้งหมดไปอยู่ในไฟล์ประเด็นตัดสินใจ
