# การรีวิวชุดเอกสาร

เป้าหมายของการรีวิวคือตอบ 4 คำถามให้ได้ด้วยหลักฐาน ไม่ใช่ด้วยความรู้สึก

1. **ถูกต้อง** เอกสารตรงกับสิ่งที่ลูกค้ากำหนดหรือไม่
2. **ใช้งานได้จริง** ถ้าสร้างระบบตามเอกสารนี้ คนจะทำงานของตัวเองได้จนจบหรือไม่
3. **ไม่ขัดกัน** ไฟล์ต่าง ๆ พูดตรงกันหรือไม่
4. **ลำดับการทำงานครบ** ทุกเส้นทางมีจุดเริ่ม จุดจบ และทางออกเมื่อไม่เป็นไปตามปกติหรือไม่

ผู้เขียนมองไม่เห็นช่องว่างของตัวเอง เพราะสมองเติมสิ่งที่ขาดให้เอง การรีวิวจึงต้องทำแบบ **เดินตามเอกสารทีละขั้นโดยใช้เฉพาะสิ่งที่เขียนไว้** ไม่ใช่อ่านผ่านแล้วพยักหน้า

## ลำดับการรีวิว

ท้ายผลการตรวจ สคริปต์พิมพ์ "จำนวนที่นับได้จริง" เช่น จำนวน Flow จำนวนประเด็นแยกตามสถานะ จำนวนแถวหน้าจอ จำนวนแถว API ให้เทียบกับตัวเลขที่เขียนสรุปไว้ในเอกสารทุกครั้งที่รัน

แก้ทุกรายการระดับผิดพลาด และพิจารณารายการเตือนทีละข้อ ก่อนไปรอบที่ 2

### รอบที่ 2 รีวิวเนื้อหา 4 ด้าน

ถ้าเรียกผู้ช่วยย่อย (subagent) ได้ ให้มอบรอบนี้ให้ผู้ช่วยย่อยที่ไม่ได้ร่วมเขียน โดยให้อ่านเฉพาะโฟลเดอร์เอกสาร ข้อมูลต้นทาง และไฟล์นี้ แล้วส่งรายการสิ่งที่พบกลับมา สายตาใหม่จับช่องว่างได้ดีกว่าผู้เขียน ถ้าเรียกไม่ได้ ให้ทำเอง โดยเปิดอ่านไฟล์จริงใหม่ทุกไฟล์ ไม่รีวิวจากความจำ

การรีวิวด้วยผู้ช่วยย่อยใช้เวลาและทรัพยากรมากพอสมควร เพราะต้องอ่านทั้งชุด สำหรับชุดเอกสารขนาดกลางขึ้นไปคุ้มเสมอ สำหรับระบบเล็กที่เอกสารรวมไม่เกินประมาณ 800 บรรทัด รีวิวเองได้

บันทึกสิ่งที่พบเป็นตารางนี้ระหว่างรีวิว

| ระดับ | ไฟล์ | สิ่งที่พบ | วิธีแก้ |
|---|---|---|---|
| ต้องแก้ / ควรแก้ / ข้อสังเกต | | | |

- **ต้องแก้** เอกสารผิดจากต้นทาง ขัดกันเอง หรือมีทางตันที่ทำให้งานจบไม่ได้
- **ควรแก้** ขาดรายละเอียดที่นักพัฒนาต้องเดา หรือคนทั่วไปอ่านไม่เข้าใจ
- **ข้อสังเกต** เรื่องที่ต้องให้ผู้ใช้หรือลูกค้าตัดสินใจ ไม่ใช่ข้อผิดพลาดของเอกสาร

#### ด้านที่ 1 ถูกต้องตามต้นทาง

ทำตารางจับคู่จาก `docs/00-source.md` และไฟล์ต้นทางจริง

1. ไล่ข้อกำหนดต้นทางทีละข้อ ทีละประโยคที่เป็นการกำหนด แล้วหาว่าอยู่ที่ใดในเอกสาร ข้อใดหาไม่เจอคือเอกสารตกหล่น
2. ไล่กลับด้าน ดูสิ่งที่เอกสารระบุเป็นข้อเท็จจริง แต่ต้นทางไม่ได้เขียน สิ่งนั้นต้องถูกบอกว่าเป็นข้อเสนอ ตามแบบการทำเครื่องหมายที่ไฟล์นั้นประกาศไว้ต้นไฟล์ และตามไปถึงประเด็นในไฟล์ประเด็นตัดสินใจได้ ดูไฟล์ฟีเจอร์เป็นพิเศษ เพราะเป็นไฟล์ที่ฝ่ายขายใช้รับปากลูกค้า
3. สิ่งที่ลูกค้ากำหนดเป็นรูปแบบตายตัว เช่น คอลัมน์ของรายงาน รูปแบบรหัส ชื่อขั้นตอน ต้องตรงตามตัวอักษร
4. ข้อแก้ไขที่ผู้ใช้ยืนยันระหว่างทาง ถูกนำไปใช้ครบทุกไฟล์หรือไม่
5. ตัวอย่างจากต้นทางที่ยกมาใช้ ตรงกับต้นทางหรือไม่

#### ด้านที่ 2 ใช้งานได้จริง

เลือกสถานการณ์จริง แล้วเดินตามเอกสารทีละขั้นเหมือนเป็นคนนั้น ทำอย่างน้อยดังนี้
- เส้นทางหลักของผู้ใช้แต่ละกลุ่ม ตั้งแต่ครั้งแรกที่เข้าระบบจนงานเสร็จ
- เส้นทางที่มีการส่งต่อระหว่างคนหรือระหว่างระบบ
- เส้นทางของผู้ดูแลระบบที่ต้องเตรียมระบบก่อนเปิดใช้
- เส้นทางที่ผิดปกติ 2 ถึง 3 แบบ ที่น่าจะเกิดบ่อยที่สุด

ในแต่ละขั้นของการเดิน ถาม 5 ข้อ
1. คนนั้นรู้ได้อย่างไรว่าถึงตาตัวเอง มีการแจ้งเตือนหรือรายการให้เห็นหรือไม่
2. มีหน้าจอให้ทำขั้นนี้หรือไม่ อยู่ในรายการหน้าจอหรือไม่
3. หน้าจอนั้นเรียก API ใด API นั้นอยู่ในรายการ API หรือไม่ และคนบทบาทนี้มีสิทธิ์เรียกหรือไม่
4. ข้อมูลที่ต้องกรอกหรือแสดง มีฟิลด์ในโครงสร้างข้อมูลหรือไม่ และข้อมูลนั้นถูกเก็บมาตั้งแต่ขั้นก่อนหน้าหรือยัง
5. ทำเสร็จแล้วเกิดอะไรต่อ ใครรับช่วง

แล้วถามเรื่องโลกจริง
- งานที่ต้องให้คนทำด้วยมือ มีใครทำ ทำบ่อยแค่ไหน ทำไหวหรือไม่
- บริการภายนอกทำสิ่งที่เอกสารอ้างได้จริงหรือไม่ มีข้อจำกัดหรือค่าใช้จ่ายที่กระทบการออกแบบหรือไม่
- นอกเวลาทำการ วันหยุด หรือเมื่อคนที่รับผิดชอบไม่อยู่ งานค้างที่ใด
- ข้อมูลตั้งต้นที่ต้องมีก่อนเปิดใช้ มาจากไหน ใครเตรียม
- ปริมาณงานจริงเกินสิ่งที่ออกแบบรองรับหรือไม่ เช่น รูปแบบรหัสที่มีเพดาน
- แผนพัฒนาส่งมอบสิ่งที่ใช้ได้ทีละเฟสจริงหรือไม่ มีเฟสใดต้องใช้ของจากเฟสหลัง

#### ด้านที่ 3 ไม่ขัดกัน

ตรวจเป็นคู่ไฟล์ สิ่งเดียวกันต้องเขียนเหมือนกันทุกที่

| สิ่งที่ตรวจ | ไฟล์ที่ต้องตรงกัน |
|---|---|
| ชื่อและจำนวนของบทบาท ประเภท ช่องทาง | ภาพรวม ฟีเจอร์ โครงสร้างข้อมูล หน้าจอ |
| ชื่อสถานะ และเส้นทางการเปลี่ยนสถานะ | ลำดับการทำงาน (ทั้งข้อความ ตาราง และผัง) โครงสร้างข้อมูล API |
| สิทธิ์ของแต่ละบทบาท | ฟีเจอร์ API หน้าจอ ความปลอดภัย |
| ตัวเลข เช่น จำนวนวัน เพดาน อายุ จำนวนรายการ | ทุกไฟล์ที่กล่าวถึง เทียบกับตารางค่าที่ตั้งได้ในไฟล์ลำดับการทำงาน และทุกแถวในตารางนั้นมีคีย์ในโครงสร้างข้อมูล |
| path ของ API | รายการ API กับรายการหน้าจอ และแผนพัฒนา |
| ชื่อฟิลด์ | โครงสร้างข้อมูล กับ API |
| จำนวนที่สรุปไว้ เช่น จำนวนหน้าจอ ข้อความ ประเด็น | ตารางสรุป กับจำนวนที่สคริปต์นับได้จริง ค้นหาตัวเลขเดียวกันในไฟล์อื่นด้วย |
| ชื่องานตั้งเวลา และรอบเวลา | ลำดับการทำงาน กับรายการงานตั้งเวลา |
| ฟีเจอร์ที่เป็นเฟสหลัง | ฟีเจอร์ หน้าจอ API แผนพัฒนา |
| ตัวเลขในตารางตัวอย่าง | บวกกันถูก และตรงกันระหว่างตาราง |

ตรวจคำด้วย สิ่งเดียวต้องเรียกชื่อเดียวตลอดทั้งชุด ถ้าเจอสองคำที่หมายถึงสิ่งเดียวกัน ให้เลือกคำเดียวแล้วแก้ทั้งชุด

#### ด้านที่ 4 ลำดับการทำงานครบ

สำหรับทุก Flow
- มีเงื่อนไขก่อนเริ่ม ขั้นตอน ผลลัพธ์ และกรณีอื่น
- ทุกทางแยกมีทางไปต่อครบทุกทาง
- ทุกจุดที่ต้องรอคนหรือระบบอื่น บอกว่ารอนานเท่าไร ครบแล้วเกิดอะไร และใครถูกแจ้ง
- ทุกการกระทำอัตโนมัติ บอกว่าอะไรเป็นตัวกระตุ้น และถ้าล้มเหลวทำอย่างไร
- บอกผลเมื่อทำซ้ำ กดซ้ำ หรือสองคนทำพร้อมกัน ในจุดที่มีโอกาสเกิด

สำหรับทุกสิ่งที่มีสถานะ
- ทุกสถานะมีทางเข้าอย่างน้อย 1 ทาง
- ทุกสถานะที่ไม่ใช่สถานะสุดท้ายมีทางออก ไม่มีสถานะที่เข้าแล้วค้างตลอดไป
- สถานะสุดท้ายระบุชัด และบอกว่าเปิดกลับได้หรือไม่
- ตารางสถานะ ผังสถานะ และข้อความใน Flow บอกเส้นทางชุดเดียวกัน ให้ไล่ทีละเส้นในผังเทียบกับตาราง
- มีทางยกเลิกหรือถอยกลับสำหรับสิ่งที่ผู้ใช้ทำผิดได้

ภาพรวมของทั้งระบบ
- ทุกช่องทางที่เรื่องเข้ามาได้ มี Flow ตั้งแต่เข้าจนจบ
- ทุกฟีเจอร์ในไฟล์ฟีเจอร์ปรากฏใน Flow อย่างน้อย 1 Flow หรือเป็นฟีเจอร์ตั้งค่าที่มีหน้าจอรองรับ
- ทุก Flow มีฟีเจอร์รองรับ ถ้า Flow พูดถึงสิ่งที่ไม่มีในรายการฟีเจอร์ ให้เพิ่มฟีเจอร์
- ถ้าลูกค้ากำหนดขั้นตอนมา ทุกขั้นของลูกค้าจับคู่กับ Flow ได้ ไม่มีขั้นใดตกหล่น
- มี Flow การเตรียมระบบก่อนเปิดใช้ และสิ่งที่ต้องเตรียมตรงกับข้อมูลตั้งต้นในโครงสร้างข้อมูล

### รอบที่ 3 แก้และตรวจซ้ำ

1. แก้ทุกรายการระดับ "ต้องแก้" และ "ควรแก้" ในเอกสาร เมื่อแก้ไฟล์หนึ่ง ให้ไล่แก้ไฟล์อื่นที่กล่าวถึงเรื่องเดียวกันด้วย
2. รายการระดับ "ข้อสังเกต" ที่ต้องให้ลูกค้าตัดสินใจ เพิ่มเป็นประเด็นในไฟล์ประเด็นตัดสินใจ
3. รันสคริปต์ซ้ำจนไม่มีรายการระดับผิดพลาด
4. ถ้าการแก้กระทบมาก คือ "ต้องแก้" กับ "ควรแก้" รวมกันเกิน 10 รายการ หรือต้องแก้เกิน 5 ไฟล์ ให้รีวิวด้านที่ 3 และ 4 อีกรอบหลังแก้ เพราะการแก้จำนวนมากมักทำให้เกิดจุดขัดกันใหม่ รอบซ้ำนี้ตรวจเฉพาะไฟล์ที่ถูกแก้และไฟล์ที่อ้างถึงเรื่องเดียวกัน ถ้าใช้ผู้ช่วยย่อย ให้ใช้ตัวใหม่และส่งรายการที่แก้ไปให้ด้วย ถ้าไม่ได้รีวิวซ้ำ ให้บอกในรายงานว่าไม่ได้ทำ

### รอบที่ 4 รายงานผู้ใช้

รายงานสั้น ๆ ตามจริง มี 4 ส่วน

1. **ตรวจอะไรไปบ้าง** สคริปต์ผ่านหรือไม่ เดินตามสถานการณ์ใดบ้าง
2. **พบและแก้อะไร** จำนวนตามระดับ และตัวอย่างรายการสำคัญ 3 ถึง 5 รายการ
3. **สิ่งที่ยังไม่ได้ตรวจหรือตรวจไม่ได้** เช่น วาดผังไม่ได้เพราะไม่มีเบราว์เซอร์ หรือข้อเท็จจริงของบริการภายนอกที่ต้องตรวจกับเอกสารของผู้ให้บริการ
4. **สิ่งที่ต้องให้ผู้ใช้หรือลูกค้าตัดสินใจ** ชี้ไปที่ไฟล์ประเด็นตัดสินใจ และบอกว่าประเด็นใดบล็อกการเริ่มพัฒนา

อย่าบอกว่าเอกสารสมบูรณ์หรือไม่มีข้อผิดพลาด การรีวิวลดความเสี่ยงได้แต่ไม่ได้รับประกัน และเอกสารที่ยังมีประเด็นรอลูกค้ายืนยันยังเปลี่ยนได้ ให้บอกสิ่งที่ตรวจแล้วและสิ่งที่เหลือ เพื่อให้ผู้ใช้ตัดสินใจได้ถูก
